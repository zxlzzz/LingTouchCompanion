# 真机验收清单

使用当前改动编出并安装 App 后，在本地照着测。每条记下：机型与系统版本、日期、结果（通过/不通过/没测）、数字、截图或日志位置。
“通过”只指真的跑过并看到结果；没跑的写“没测”。

首轮顺序：编译安装 → 前台双流 → 直连与外供电 Hub → 拔插、拒绝授权及启动中断开 → 后台与息屏至少 10 分钟。先确认前台收到深度和彩色，再测后台。

## 0. 准备

1. 当前工作区已经使用 `apps/android/` 和 `apps/harmony/`，不需要迁移。只有仍使用 2026-10-28 之前旧目录的工作副本才需要历史迁移脚本，先演练并检查输出：
   ```powershell
   powershell -ExecutionPolicy Bypass -File docs\migrate_local_2026-10-28.ps1 -DryRun
   ```
   ```powershell
   powershell -ExecutionPolicy Bypass -File docs\migrate_local_2026-10-28.ps1
   ```
2. 电脑上跑一遍核心测试（需要 CMake 和 C++17 编译器）：
   ```bash
   cmake -S core -B build/core && cmake --build build/core && ctest --test-dir build/core --output-on-failure
   ```
3. 编出并安装要测试的 App：安卓用 Android Studio 打开 `apps/android/`；鸿蒙用 DevEco Studio 打开 `apps/harmony/`（签名自己配，签名文件不进仓库）。调试 APK 在 `apps/android/app/build/outputs/apk/debug/app-debug.apk`。编译成功不等于实机验收。
4. 供电：CS30 手册写 5V、平均 0.6A、约 3W，描述符里的 500mA 不作数。手机/平板带不动（开流失败、反复断开）就接带电源的 Hub 或分线器，记下用的是哪种。


## 1. 安卓：深度和彩色、插拔恢复

工程基线为 Android 10 / API 29 以上、ARM64。实现和固件限制见 [采集说明](cs30_mobile_capture.md)。

1. 「连接相机」→ 授予 CAMERA / USB 权限。先显示等待，实际收到完整双流和标定后才显示“正在接收深度和彩色”；记录启动到首帧的时间，不能把成功提交请求当成已收帧。
2. 记录诊断中的固件、会话、USB 批次、完整载荷、不完整载荷、坏载荷、包错误、标定 ID、彩色尺寸，以及实测处理帧率。停止时旧帧和栅格应立即失效。
3. 在 native `SensorAdapter::get_latest_frame(0, frame)` 检查 640×480 深度和 960×540 JPEG；把 `frame.color->jpeg` 导出，用独立 JPEG 解码器验证实际图像尺寸及内容。两端已有并排的彩色/深度预览，保存按钮仍只导出深度。确认彩色内容真实、深度轮廓和场景对应，停止/重连时旧画面消失，后台返回后恢复新画面。只看到栅格不能判定彩色验收通过。
4. 固定相机与场景，把手机保存的 `latest_frame.bin` 与 PC 厂家 SDK 后续采集比较：`python perception/cs30/compare_frames.py latest_frame.bin PC.raw`。两次曝光不承诺哈希相同。另核对 RGB 内参缩放、R/t 单位与方向，以及深度到彩色的对应点；标定仍是 inferred。
5. 连续插拔至少 20 次，分别测直连和外供电 Hub。记录成功率、首帧时间、恢复次数；授权拒绝不得循环重试。可恢复错误最多按 1/2/4 秒重试三次，重新插入应重新枚举，后台缺权限应提示回前台授权。
6. 连续点击连接/断开、启动中拔线、重启取流、切换页面；界面不能因长控制请求卡住，不能复用旧会话的帧。记录 USB 接管失败、带宽不足和电源断续的原始日志。

## 2. 鸿蒙：系统等时队列、真实取消回调

工程基线为 HarmonyOS 5.1 / API 18 以上。运行当前主界面的双流连接路径，同第 1 节全部步骤，另核对：

1. DevEco 的 ArkTS 类型检查和原生 NDK 构建均通过。没有 SDK 编译或没连设备的项目一律写“没测”。
2. 接口描述符包含接口 1 / alt 1 / 等时 IN 端点 0x82；找不到时应明确失败，不伪造 alternate 描述符。
3. 核对回调的数据实际写入申请的 buffer，当前每请求默认 8 包，降级时为 4/2/1 包。尾包和空微帧是正常现象；记录公开标志 `USB_TRANSFER_SHORT_NOT_OK` 在目标系统上是否错误拒绝正常等时短包。发生错误时保存状态和每包实际长度。
4. 停止时禁止重提，取消后等真实回调排空，最后才 release / closePipe。测试正在收帧、设备已拔出、启动失败三种状态。鸿蒙单次取消排空最多等待 3 秒，若取消没有回调应返回超时、保留在途缓冲，后续补齐回调后仍可重试关闭与重连；不得用固定等待后释放在用缓冲。
5. 重连后旧 epoch 的包和事件不得更新结果。应用不再默认走 getFileDescriptor + libusb 的实验路径；旧工具接口不纳入本次主路径验收。

## 3. 两边喂同一帧，核心输出的 9×6 完全一致

1. 找一帧有地面的真实数据：任一台设备上对着有地面的场景「保存当前帧」，拷到电脑；先在电脑上跑
   ```bash
   build/core/perception_tests/lt_frame_tool grid latest_frame.bin perception/cs30/calibration_0.bin
   ```
   记下最后一行的“摘要”。
2. 把这帧改名为 `frame.bin`，分别放进两台设备的应用目录（安卓：`adb push frame.bin /sdcard/Android/data/com.lingtouch.companion/files/`；鸿蒙：`hdc file send` 到应用沙箱的 files 目录），两台都先连一次相机（让核心读到同一台相机的标定），再点「核对帧文件」。
3. 三处（电脑、安卓、鸿蒙）的摘要应完全相同。摘要覆盖 54 格、每格诊断、各阶段像素数、地面法线和高度的二进制位。不同的话把三处显示的栅格和摘要都记下来。

## 4. 息屏 / 后台至少 10 分钟，持续取流、计算、发蓝牙不停

先做一次前台连续 30 分钟：每 5 分钟记录预览旁的完整组数、彩色/深度帧号，以及详情中的生成耗时、等待超时、显示重置、待释放图像、页面刷新最大延迟和 USB 坏包。约 10 分钟附近重点观察。若画面停止，先记录上述值是否增长，再重启取流；采集持续而预览停止与 USB 收不到完整帧应分开定位。模拟测试不能替代这一条。

1. 连上相机和手柄，选好状态 2 的表示方式，打开「持续发送」；鸿蒙另打开「后台运行（长时任务）」。
2. 记下「完整载荷」「已处理帧」「已发帧」「手柄确认刷新」四个数，然后息屏（或切到别的应用）≥ 10 分钟。
3. 亮屏回来再记四个数：都应持续增长；用差值除以时间得到后台期间的帧率和发帧率。手柄在息屏期间应一直在刷新（手摸确认）。
4. 安卓用的是 connectedDevice 类型前台服务 + PARTIAL_WAKE_LOCK；鸿蒙是 bluetoothInteraction + location 长时任务（“计算任务”只开放给 2in1，平板用不了）。被系统停掉时记下停在第几分钟、哪个数先不涨。

## 5. 发一帧到手柄（旧板 V2.8 固件），手摸确认位置和方向

1. 「扫描并连接手柄」→ 状态“已连接”。
2. 在相机前方放一个箱子（例如右前方约 2 m），界面上对应格应为 ■；选平或凸后「发送一帧」。
3. 手摸：凸起的点应落在与界面一致的左右、远近位置。最远的 4 行（旧板 10×9 的前 4 行）应全平。
4. 方向有三个开关，都在 `core/config/lingtouch_defaults.conf`：
   - `tactile.module_rot180`（模组 180° 反装，与 frame_converter.py 一致，默认 true）；
   - `tactile.mirror_left_right`（穿戴左右镜像，沿用 experiment_server.py 和 9/29 比赛版的做法，默认 true）；
   - `depth.image_mirrored`（CS30 深度图本身是否左右镜像，未确认，默认 false）。先看界面：物体放在左边，界面左列应亮；不对就是 `depth.image_mirrored`。界面对了、手摸反了，就是 `tactile.mirror_left_right`。
5. 状态 2：分别选平和凸各发一次，确认没有数据（全是 ?）时整片平或整片凸。最终用哪种，定了之后写进 `tactile.unknown_cell_policy`。

## 6. 彩色固件兼容

当前实现按官方 SDK 4.2.5.0 的 CS30 JPEG 载荷分支解析：深度后接 LE32 JPEG 长度及 JPEG，深度与彩色共用一组帧号。老固件的 NV12 类分支尚未实现。记录实际固件原始值、双流载荷样本、JPEG 尺寸；若 5 秒无完整帧，检查坏载荷、供电和固件，不能只看 USB 回调在涨就判定成功。不要为测试擅自刷固件。

## 7. 深度是光轴 Z 还是径向距离、要不要去畸变（平面检查）

1. **判 Z / 径向**：相机正对一面平整的墙，距离 1–2 m，墙填满画面中央，点「平面检查」。四种假设按残差排序，最小的那组的“含义”就是答案（合成测试里：对的 < 1 mm，错的 > 5 mm）。正对墙时，光轴 Z 深度在整面墙上是常数，去不去畸变墙都一样平，所以这一步只看含义。
2. **判去不去畸变**：斜着拍一个大平面（例如相机俯仰约 45° 看地面，地面填满画面中央），再点一次。同一含义下“去畸变”和“不去”的残差差别大，小的那个是答案。
3. 把结论写进 `depth.meaning`、`depth.undistort`，并把两次的四行结果抄进报告。也可以「保存当前帧」后在电脑上跑 `lt_frame_tool plane 帧文件 perception/cs30/calibration_0.bin`。
