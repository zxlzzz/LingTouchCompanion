# CS30 手机端采集实现与验证边界

数据路径：系统 USB 授权 → 接管接口 → 顺序执行 CS30 控制请求 → Probe/Commit → 异步等时接收 → UVC 拆帧 → 一组深度和彩色 → `SensorAdapter::get_latest_frame`。主应用同时把完整帧的深度交给 `Engine::submit_frame` 后台计算，USB 回调不做几何推理。彩色保留为 JPEG；鸿蒙另通过 `cameraPreview(afterFrameId)` 拉取同组彩色 JPEG 和深度显示数据，未增加配准算法。

鸿蒙长时路径（2026-11-20）：系统回调把小批次复制到固定容量的原生接收队列后即可补交接收，独立拼帧线程再执行上述完整帧交付。停止/切换会话会隔离旧队列并等待执行中的交付结束；队列溢出作为中断报告，不无声丢批次后继续组合图像。取消超时只结束等待并保留系统仍占用的缓冲，不把超时当作已取消。相机控制独立于共享异步线程池，预览对未完成的 SDK 任务实行每通道最多一个旧任务加一个当前任务的上限。全部 `SensorAdapter` 接口、采集分辨率和算法判定阈值保持不变。

鸿蒙页面每 200 ms 拉取预览快照，不重复解码同一帧。彩色异步解码到 480×270，深度缩为 320×240 灰度图，固定 0.1–5 m，近亮远暗、无效黑色；只用于观察，不改变计算输入。原生层只保留一个按预览需求复制的完整采集组，后台无预览需求时不逐帧复制。彩色和深度独立处理，每路最多一个 SDK 任务在途，显示进度可以不同，原始采集组仍是配对的双流。停止、重连和切到后台会清除显示并丢弃旧会话的解码结果；USB 采集和后台任务保持原有行为。

2026-11-19 用户反馈约 10 分钟后两幅画面均停住，没有明显发热或息屏。代码确认旧预览串行等待彩色解码、ImageSource 释放后才生成深度；这些等待任一不返回，会阻塞两路预览。另有逐采集帧复制完整图像、每次 USB 回调分配描述数组、每次页面轮询重建未变化栅格等额外开销。现将两路 SDK 工作分离，每路等待超过 2 秒给出具体提示；不通过持续提交新任务来替代仍未结束的 SDK 操作。旧 PixelMap 释放完成前按每路最多两个待释放任务限流；缺失 Image 显示回调超过 2 秒时清除图像并重置该路显示，避免队列无限增长。SDK 永久不返回时对应通道仍需系统操作结束或重启应用，不能承诺在同一进程中取消该 SDK 任务。

USB 包描述改为槽位复用，原生描述暂存用固定容量数组。原生完整图像快照按预览拉取需求复制，诊断字符串每秒更新；页面栅格仅在内容变化时重建，详情每秒刷新，后台停止页面轮询。连接参数、有效完整帧 5 秒超时与有界恢复流程保持原有行为。

`cameraStatus` 新增当前会话完整组数、最新采集帧号、距完整帧时间和预览复制次数，`cameraPreview` 通道参数为 1=彩色、2=深度、3=两路（默认）；一侧忙时不生成/复制另一侧不需要的数据。预览旁显示采集与两路画面帧号，详情显示生成耗时、等待超时、显示重置、待释放数量及页面刷新最大延迟。采集组数增长而预览帧号不增长，指向显示链路；回调增长而完整组数不增长，需查坏包/载荷；回调也停止，需进一步查 USB/设备/事件循环。这些分辨仍需结合真实故障现场，不能把软件优化当成已确认并解决实机唯一根因。

栅格主状态不再拼接逐帧数值；地面诊断单独显示，每秒更新一次，状态变化立即更新。`ground.max_below_fraction=0.05`、`ground.below_margin_m=0.10` 保持不变：提示“40% 的点低于拟合平面 0.10 m 以上”表示约 40% 的采样候选点低于候选平面超过 10 cm，不是丢包率或置信度。当前拟合结果因此被拒绝，栅格保持未知；其原因需结合真实深度帧、相机姿态及平面检查判断，不能仅凭该比例确认是桌面或标定问题。

安卓随后同步加入上述双预览和诊断分离。JNI 使用标准数组元素数语义，不存在鸿蒙 TypedArray 单位差异；原生包描述仍校验数量、长度与槽位偏移。取流改为最大每请求 8 包，同步提交 I/O/内存错误按 8→4→2→1 包有限尝试，每轮先排空取消回调，不把所有 I/O 错误都解释为内存不足。预览快照和平面检查通过服务工作线程访问原生句柄，JPEG 解码在另一个线程，停止/重连由 epoch 丢弃旧结果。入口 C++17 和 16 KB 页适配已纳入安卓构建。

安卓由 `UsbManager` 打开、强制接管接口，原生层仅包装已授权 fd，不扫描 `/dev/bus/usb`。系统连接在原生请求排空和 libusb 关闭之后释放。鸿蒙由原生工作线程发请求，通过线程安全回调交给 ArkTS 执行 `usbManager`，再异步完成原生等待，避免阻塞 ArkTS 事件循环。

## 流格式与依据

默认同时请求 **640×480 深度 + 960×540 彩色**。适配器另提供 320×240 深度、1920×1080 彩色和纯深度组合。配置来自 CS30 SDK 支持列表，尚未逐组合真机验收，不代表已证明所有固件支持。

本次只读检查官方 `SynexensSDK_4.2.5.0_armv8_202602060238.tar.xz` 中的接口头和 ARMv8 库，没有把 SDK 二进制加入项目。该库依赖 Linux glibc，不能直接当 Android 库使用。新增协议判断依据：

- `SYDeviceCS30::SetFormat`：25 字节分为 RAW、DEPTH、IR、RGB、AI 五槽，每槽 LE16 宽、LE16 高、1 字节类型。深度槽类型为 2，RGB 槽类型为 3。枚举序号不直接用作线上的类型值。
- `SYDeviceCS30::ProcessFrameDataInside`：深度和彩色在同一 UVC 载荷中；JPEG 分支在深度后读取 LE32 彩色长度，再取 JPEG。代码检查 JPEG 边界、SOF 尺寸及长度，不把深度尾部猜成彩色。
- SDK 的固件版本判断为 `> 0x000702ff` 时走上述 JPEG 分支；较早版本有 NV12 类分支。**本次未实现旧分支的彩色转换**，这类载荷会被拒绝，5 秒无完整帧会报告中断。需要记录真机固件号和双流样本后才能扩展，不能把协议推导当成全固件验证。
- UVC 协商仍可能描述 640×480 的外层容器。因此 Commit 使用本机实际 Probe 返回值；双流拼帧上限同时覆盖所选深度和彩色的保守容量，硬上限 8 MiB，不按旧的 614400 字节截断双流。

彩色默认选 960×540，是因为现有标定 blob 的彩色内参参考 1920×1080；两者宽高比相同，可以等比例缩放。暂不暴露 640×480 彩色，避免在裁剪规则未知时错误缩放。深度标定按输出分辨率选择对应完整 blob，彩色内参和深度到彩色的 R/t 同时验证。所有这些标定仍保留 `inferred=true`，平移单位、方向、像素对应关系和深度 Z/径向含义仍需与真机 SDK 比较。

深度转换为行优先 uint16 毫米，0 表示无效，设备保留值 1–10 也归零。时间戳是拼帧完成时的主机单调时钟，与现有原生 IMU 时钟同源；不是硬件曝光时刻。同载荷只表示同一采集组，未证明两传感器曝光严格同步。

`get_capture_settings` 已实现状态检查和可选字段返回；未证实的帧率、积分时间及范围留空。原始 `0xa300` 寄存器值不冒充微秒，UVC 外层帧间隔不冒充实际采集帧率。

## 连接、停流和恢复

- 控制请求沿用已抓取的启动顺序与 15 秒超时，接收队列在切换到 alt 1 后立即挂载；仅保留已有的 270 ms 设备等待。
- 鸿蒙单次等时请求上限为 8 包（当前每包 3072 B，即每请求 24 KiB），保留 10 个并行请求。同步提交遇到 `14400012` 时，取消并等待已提交请求的真实回调排空，再按 8→4→2→1 包有限重试；其他错误不触发此降级。减少的是单次请求包数，每包长度和双流分辨率不变。实际大小及尝试序列并入现有诊断信息，重提失败保留系统错误码和文字。
- 固定大小深度和可变大小双流分别拼帧。包错误、坏 UVC 头、ERR 位都会污染整帧，不能靠后续数据补足长度后交付。
- 鸿蒙回调进入原生层之前校验每包描述：错误状态、负数/非整数/超长的实际长度作为坏包交给拼帧器，丢弃受影响帧并继续接收；返回包数或槽位长度不符时丢弃整批并标记帧受损，避免推算不可信的后续偏移。诊断记录坏包数和首个异常描述。持续没有有效完整帧仍由 5 秒监控报错，原生参数检查保留，并在负长度错误中附带包号及数值。
- 只保存最新完整帧，帧号在同一适配器对象内持续递增；无新帧、未授权、设备断开、标定缺失、配置不支持分别返回状态。出参只在成功时更新。
- 停流先禁止重提、取消请求、等待实际回调排空，再释放传输资源。鸿蒙没有用固定 sleep 假定取消已完成。系统若始终不交付取消回调，鸿蒙桥会报告操作超时，并保留尚未排空的缓冲和 pipe；不能强行释放仍在使用的资源。
- 旧会话的包和异常回调会被丢弃；停止、关闭、断线时清最新帧及计算结果，计算线程也不能重新发布上次会话的结果。
- 第一帧或后续完整帧超过 5 秒未到，报告取流中断。两端对可恢复错误按 1、2、4 秒最多重试三次，正常收帧满 10 秒后恢复重试预算。重新插入会重新枚举；授权失败不循环弹窗，也不在后台发起授权。
- 安卓界面轮询使用状态快照和非阻塞诊断读取，不等待长控制请求。鸿蒙连接操作返回 Promise，系统 USB 请求仍可在事件循环执行。

## 系统与后台运行

安卓保持工程现有 **Android 10 / API 29 以上、ARM64** 基线。需要 USB Host/OTG、CAMERA 和 USB 授权，使用 connectedDevice 前台服务及开流期间的 PARTIAL_WAKE_LOCK。直连与外供电 Hub 都走同一接口；软件无法补足手机端供电。速度未知时继续尝试并记录，明确低速/全速连接会拒绝。

鸿蒙保持工程现有 **HarmonyOS 5.1 / API 18 以上** 基线，系统等时接收 API 不支持更早版本。采集控制器由页面之外的实例持有，页面隐藏不关闭相机，Ability 销毁时主动停止。既有长时任务需要由用户启用；当前工程声明的蓝牙交互/定位类型只适用于真实满足系统条件的业务，**没有通用的 USB 相机后台保活许可，不能保证所有普通手机息屏持续采集**。SDK 编译、任务资格及目标机息屏测试仍是交付到设备的必要步骤。

官方 USB 资料：[OpenHarmony usbManager](https://gitee.com/openharmony/docs/blob/master/zh-cn/application-dev/reference/apis-basic-services-kit/js-apis-usbManager.md)、[官方 NAPI 参数转换源码](https://github.com/openharmony/usb_usb_manager/blob/master/interfaces/kits/js/napi/src/usb_info.cpp)。API 18 公开的传输标志枚举以 `USB_TRANSFER_SHORT_NOT_OK=0` 起始，本实现使用其公开名称；没有虚构“无标志”枚举。等时短包按每包实际长度处理，仍需真机确认系统实现没有错误拒绝正常尾包。

随后真机截图先出现步骤 0 控制请求返回 -1，断电重试后出现“无法继续提交 USB 接收：undefined 等时包长度不能为负数”。对应 21:21 左右的历史日志含等时提交和包回调记录，说明该次尝试已进入接收阶段；负值来自哪个具体字段尚无原始数值证据。新增上述描述校验、坏帧丢弃及原始异常数值诊断，扩展主机回归与 DevEco 签名 HAP 构建通过；该版已通过 HDC 覆盖安装到平板并启动，等待相机接回后复测真实首帧。

进一步实测错误明确为“包 8 length=-2001956872 actualLength=91 status=0”，但请求只有 8 包（索引 0–7），据此定位到桥接层读取超出描述视图范围。官方 [Node-API 与标准接口的差异说明](https://github.com/openharmony/docs/blob/master/zh-cn/application-dev/reference/native-lib/napi.md#napi_get_typedarray_info) 明确：OpenHarmony 的 `napi_get_typedarray_info` 出参 `length` 是字节数，Node 的是元素数；原先的共同假设把 96 B 的 Int32 描述视图重复乘 4，按 384 B 解析。此前把该负值视作设备坏包的判断需更正。

修复将新旧两个 NAPI 入口的字节视图转换集中到 `napi_bytes.h`，按 `__OHOS__` 区分返回单位，并校验底层 ArrayBuffer 容量、视图偏移和字节对齐。主采集路径直接传描述的 ArrayBuffer，避免依赖 TypedArray 长度语义。回归用包含 8 个描述、非零偏移且周围填充负数的视图，验证不越出视图；另以测试专用 `tools/ohos_napi_shim` 在主机复现鸿蒙字节数语义，运行同一真实插件的采集和旧入口测试。Node 与鸿蒙语义两套回归及 DevEco HAP 构建均通过，该版已重新覆盖安装到平板并启动；真实相机首帧仍待确认。
